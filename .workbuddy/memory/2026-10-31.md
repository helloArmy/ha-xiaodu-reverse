### 两仓库控制方式对比结论（已逐行比对 api.py / XiaoDuAPI.py）

协议层**几乎逐字节相同**，同一套小度云 API：

| 环节 | 接口 |
|---|---|
| 认证头 | `Cookie: BDUSS=x;BDUSS_BFESS=x` + iPhone UA + `device-id: deviceid` |
| 会话校验 | POST `/appserver/gateway/app/v1`（`dueros://smarthome.bot.dueros.ai/gateway/myspeaker`）|
| 房屋 | POST `/saiya/smarthome/multihouse` `HOUSE_LIST` |
| 设备列表 | POST `/saiya/smarthome/appliance` `GET_USER_ALL_APPLIANCES` + `HOUSE_ID` cookie |
| 详情 | GET `/saiya/smarthome/appliancedetails` body `{applianceId,version:2,from:"h5"}` |
| 控制 | GET `/saiya/smarthome/directivesend?from=h5_control` |
| 状态 | `appliance.stateSetting.<attr>.value` |

真正的差异只有三处：

1. **面板控制**：hass_xiaodu 的 `switch_panel_on/off` 多一个 `payloadObject`，能把 `panels[].list[].actions[].payload` 原样透传 —— 部分厂商设备不带这个 payload 就控制失败。**hass_xiaodu 更强，已采纳。**
2. **空调/风机**：ha-xiaodu 有 `SetTargetTemperatureRequest` / `SetFanSpeedPercentageRequest` / `SetFanOscillationRequest`；hass_xiaodu 只有 Increment/Decrement（加一度逼近）。**已作为增强并入。**
3. **鉴权失效**：ha-xiaodu 抛 `LoginExpired` → 触发自动重登；hass_xiaodu 只返回 `[False, "cookie失效"]`。**已采纳 ha-xiaodu 的异常体系。**

### 落在代码里的对应关系

- `login.py` — 逐行移植 ha-xiaodu：RSA(1024) 分块小端、moonshadV3 逐日轮换 AES key、屏幕混淆 md5 交织、双层 base64、shaOne 循环、400023 短信验证
- `api.py` — hass_xiaodu 的控制语义，但用 dict 合并替代它的**字符串拼 JSON**写法；保留 `switch_panel_on(switchType, typeValue, headerNameOn, headerNameOff, payloadObject)` 参数含义
- `coordinator.py` — 批量 `GET_APPLIANCES_BY_ID` 一次拉全部，缺 `stateSetting` 再逐台 `appliancedetails` 回退；`not login` 时用配置里存的账密自动重登并回写 entry
- `appliance_types.py` — 类型表 + `panels.功能控制` 解析（一项功能 = 一个实体）

## 踩过的坑 / 决定

- **`_seed` 机制**：批量接口有时不返回 `panels`，但实体初始化需要它。setup 时先并发拉一次全量 detail 存 `coordinator._seed`，`get_appliance` 优先 `data` 再回退 `seed`。
- **单房屋自动跳过选择步骤**（`_after_auth` 里 `len(house_list)==1` 直接进 device）。
- **`super().__init__()`**：ConfigFlow/OptionsFlow 的 `__init__` 必须调，否则新版 `OptionsFlow.config_entry` property 依赖的 `_config_entry_id` 未初始化。
- **`climate` 加 `_enable_turn_on_off_backwards_compatibility = False`**，避免 HA 2024.2+ 的弃用告警。
- **`sensor` 的 device_class 用 `getattr(SensorDeviceClass, name.upper(), None)` 兜底**，避免版本差异导致 AttributeError（如 `FORMALDEHYDE`）。
- 验证手段：**`py_compile` + AST 跨模块符号检查**（`from .api import X` 的 X 是否真在 api.py 顶层）+ JSON/翻译键对齐。本机无 HA，无法运行期验证。

### 认证方式（重要，以后直接用）

1. `POST /auth/login_flow` body `{client_id, handler:["homeassistant",null], redirect_uri}` → `flow_id`
2. `POST /auth/login_flow/{flow_id}` body `{client_id, username, password}` → `{type:"create_entry", result:"<code>"}`
3. `POST /auth/token` **form-encoded** `grant_type=authorization_code&code=..&client_id=..` → `access_token`（expires_in 1800）

### 三个真实 bug（都已修复并验证）

1. **`VacuumEntityFeature.BATTERY` 在 HA 2026.10 已移除** → 类体硬引用导致 `vaccine` 平台 ImportError → 整个 setup 失败（`setup_error`）。
   修复：`getattr` 容错构造 features。climate 同样处理。
2. **`XiaoDuEntity.state()` 覆盖了 `Entity.state` property** → `str(self.state)` 得到 bound method → 其 repr 又引用实体 → `__repr__ → _stringify_state → available → __repr__` 无限递归（`RecursionError: Stack overflow, 993 kB`）→ 所有实体 `Error adding entity` 且恒为 `unavailable`。
   修复：`state() → attr_value()`，`is_on() → attr_is_on()`。**教训：绝不可用 `def` 覆盖 HA Entity 的 property；已加 AST 静态检查。**
3. **空调温度指令实测行为**（海信爱家）：
   - `SetTargetTemperatureRequest` → `header name is not vaild`（指令名不存在）
   - `IncrementTemperatureRequest` → `控制失败，请检查该设备的电源和网络是否正常`（指令有效，**关机时设备拒绝**）
   - 原实现两者失败后**静默返回 200**，界面无反应也不报错。
   修复：增减优先 → 直接设温兜底 → 仍失败抛 `HomeAssistantError` 并提示关机时先开机。
